# 同時入力の設計（バイタル・食事を欄ごとにサーバーで裁く）

複数の端末が同じ利用者・同じ日のバイタルや食事を同時に入力しても、**どちらの値も黙って消えない**ようにするための設計。
判定（書いてよいか）と書込を、サーバーの関数の中で同じトランザクション・同じ行ロックの下で行う。
端末は「何を・何を見て書いたか」を送るだけで、書くかどうかは判定しない。

- 対象: バイタル（vitals）・食事（meals）・申し送りの既にある行の変更と取り消し（notes。2026-09-29 追加＝§9）
- 対象外（従来の送り方のまま）: 水分（fluid_intake）・申し送りの新規登録（notes の insert・client_key）・外出（outings）・既読（note_reads）・出勤者（attendance）・申し送りでの表示名（residents.note_alias）

## 1. なぜサーバーで裁くか

端末で「読んで比べてから書く」方式は、読み取りと書込の間に必ず時間差がある。追い越し・自分の値どうしの食い違い・送信中の上書きなど、
端末側の継ぎ当てでは閉じきれない。判定と書込を1つの関数の中（行ロックの下）で行えば、これらは構造的に起きない。

## 2. サーバーの関数 `apply_cell_edits`（`supabase/migrations/0011_apply_cell_edits.sql`）

```
apply_cell_edits(
  p_table      text,                -- 'vitals' | 'meals' | 'probe'（関数があるかの確かめ）
  p_key        jsonb,               -- 定時バイタル: {resident_id, measured_on}
                                    -- 食事: {resident_id, meal_on, meal_slot}
                                    -- 定時以外のバイタル: {client_key, resident_id, measured_on, kind}（作れる）または {id}（直すだけ）
  p_edits      jsonb,               -- {欄: {value, base}}。base＝その欄を直し始めた時に画面に出ていたサーバーの生の値
  p_fill       jsonb default '{}',  -- {measured_at, recorded_by}。空いている時だけ埋める（判定には使わない）
  p_editor     bigint default null, -- edited_by（1欄でも書いた時だけ）
  p_client_key text default null    -- 定時以外の新しい行の冪等キー
) returns jsonb
-- {version:1, status:'applied'|'partial'|'conflict'|'noop'|'probe',
--  row:{アプリが読む列}|null, applied:[欄], settled:[欄],
--  conflicts:[{field, server, base, mine, reason:'changed'|'missing'}]}
```

### 2.1 欄ごとの判定（行ロックの下）
1. サーバーの値＝あなたの値 → `settled`（もう載っている。書かない）
2. サーバーの値＝基準 → 書く（`applied`）。基準が分からない欄（base キーが無い）は、サーバーが空の時だけ書く
3. それ以外 → 競合（`reason:'changed'`。他の端末が先に変えた）

- **血圧の上と下（sys_bp / dia_bp）は1つの組**。片方が競合なら、送られてきた相方も書かず、「載っている」ともせずに競合にする（組の判定は 1 より優先）。
  誰も測っていない上下の組み合わせを作らないため。相方の reason は競合した側と同じ
- 1欄でも書いた時だけ、`edited_by` を書き、`p_fill` の欄を空いていれば埋める。rev はトリガで進み、変更の記録（record_history）もトリガで残る。
  書く欄が無ければ行に触れない（rev を進めない）
- 行が無く、全ての欄の基準が空 → 新しい行を作る（定時・食事は自然キー、定時以外は冪等キー）。同時に作られた時は部分一意索引で吸収して取り直す
- 行が無く、基準のある欄がある（＝取り消された行への編集）→ 全欄を `reason:'missing'` の競合で返す（行を復活させない）
- 取り消し済みの行（deleted_at あり）は対象にしない
- 送る値は列の精度にそろえる（体温は小数1桁など）。基準は画面で整形した値ではなく、サーバーが返した生の値を使う

### 2.2 関数の約束
- volatile（読み取り専用のトランザクションでは呼べない）。PostgREST からは POST で呼ぶ
- security invoker（呼んだ職員の権限＝各表の行レベルセキュリティがそのまま効く）。`search_path` は固定
- 実行権限は authenticated のみ（anon・public は不可）。作り直しは drop → create（多重定義を作らない）
- 動的 SQL を使わない（書ける列は関数本文に固定。未知の欄名は拒否）

## 3. 端末の送信待ち

### 3.1 localStorage のキー

| キー | 中身 | 形 |
|---|---|---|
| `cl_sendQueue` | 水分・申し送り・外出・既読・出勤者・表示名の退避 op | `{ ops: [op…], brokenRaw? }`（この仕組みより前の版と同じ形） |
| `cl_sendQueue2` | バイタル・食事の送信待ち（1行＝1エントリ）と、送信済み・取り下げた版の記録 | `{ ver: 2, rows: {行キー: エントリ}, done: [記録…], brokenRaw? }` |

- `cl_sendQueue` にバイタル・食事の op が見つかったら（旧ビルドが積んだ分など）、`cl_sendQueue2` の行へ読み替えて移す。
  `cl_sendQueue` から外すのは、`cl_sendQueue2` に書けたことを読み直して確かめた後だけ（書けなければ外さない＝消さない）
- 旧ビルドは `cl_sendQueue` の `ops` だけを読み書きし、`cl_sendQueue2` には触れない
- 読めなかった原文は、読んだキューの `brokenRaw` に畳んで持ち続ける（消さない）

### 3.2 行キーとエントリ
- 行キー: 定時 `vitals@<利用者>|<日付>|routine`／食事 `meals@<利用者>|<日付>|<食事枠>`／定時以外の新しい行 `vitals~<冪等キー>`／行 id で指す行 `vitals#<id>`（`meals#<id>` は旧形式の読み替えだけが作る）
- エントリ: 表・行の指し方・欄ごとの `{value, base, at, ver}`・空いていれば埋める欄・記入者・状態（`pending`／`conflict`／`rejected`）・書かなかった欄・再送の回数と時刻
- 欄の値は**後勝ち**、基準は**先勝ち**（送信待ちの自分の値を基準にしない）
- 版（ver）はタブの印と連番。旧形式から読み替えた欄の版は、op の識別子・欄・**値の指紋**から作る（同じ版＝同じ値）
- 冪等キーで作った行は、応答で分かった行 id を覚える。画面が行 id で指しても、見る・送る・取り下げるのは作った時の行キーの控え

### 3.3 保存と送信（経路は1本）
`saveVitalEdits(target, edits, opts)`／`saveMealEdits(...)` が、送信待ちに欄を書く → 書き戻す → すぐ送る → その行の結果を待つ。

- 通信できれば `{status, row, applied, settled, conflicts}`、できなければ `'queued'`、サーバーが拒否したら例外（送信待ちには `rejected` として残る）
- 止まっている行（conflict）へは、〔くらべて選ぶ〕で選ぶまで送らずにまとめる（`held`）
- `opts.rebase` … 画面が最新を見て選んだ送信。基準を置き換え、止まった行を送る状態へ戻す
- `opts.dropVers` … 同じ行の欄を、見た版のまま取り下げてから送る（食事の〔両方残す〕）。書けた・送信待ちにできた時だけ確定し、拒否・競合なら元に戻す
- `opts.asNew` … 〔新しい行として保存〕。同じ行の送信待ちの全ての欄を「空欄を見て書いた」（基準は空）にそろえ、空にする欄は外す
- 応答が来たら、書けた欄・載っていた欄は送った時と版が同じ時だけ消す（送信中に打ち直した欄は残す）。書かなかった欄は `conflict` として残す。
  組の相方が競合なら、片方だけを消さない
- 送信は Web Locks（`cl_sendQueue_flush`）で1タブずつ、行ごとに古い入力の順
- 旧形式から読み替えた行 id の行（食事・定時バイタル）は、送る直前に1行読んで自然キーへ付け替える。止まった（競合・拒否）行も、送信の機会に読み取りだけで付け替える
  （画面から見えるようにする。行が取り消されている・読めない時は行 id のまま残し、未送信に数え続ける）

### 3.4 書き戻しと別タブ
- 書き戻しはすべて Web Locks（`cl_sendQueue_write`）の中で「読み直し → 和集合 → 書き戻し」
- 和集合は欄単位。両方にあれば新しい版、片方にしか無ければ残す。捨てるのは**送信済み・取り下げた・後の入力に置き換わった版の記録（done）と同じ版**の時だけ
  （「保存先から消えていた」だけでは捨てない）。記録は24時間・1000件まで持つ
- 旧ビルドのタブが同じ op に重ねた値は別の版になり、送信済みとはみなさない。新しく現れた読み替えの版は、いま観測した入力として扱う

### 3.5 画面へ渡すもの
- `pendingRow(table, target)` … その行の送信待ち（値・基準・状態・書かなかった欄・版）。送信待ちの重ね表示と、止まった行の「あなたの入力」はここから読む
- `discardPendingRow(table, target, fields?, vers?)` … 取り下げ。`vers`（画面が見た版）を渡すと、その版のままの欄だけを外す。血圧は組で外す
- 関数が無い DB では旧経路へ落とさない。入力の可否を確かめる時に `probe` し、無ければバイタル・食事の入力を止めて「サーバー側の更新待ち」と出す

## 4. 画面（バイタル一覧・バイタル一括・食事一覧・食事一括・日報のバイタル欄）
- 送信待ちの値は「⚠ 未送信」の印つきで重ねて出す。未送信件数の通知を受けたら送信待ちを引き直し、送り終えた行の印を外す
- 競合は「先の値／あなたの入力」を併記し、〔くらべて選ぶ〕を出す
  - 〔先の値を残す〕… あなたの入力（開いた時に見せた版）を取り下げる
  - 〔自分の値で直す〕… 基準を取り直した最新の値にして送り直す。血圧は組で送る
  - 〔両方残す〕… バイタルは新しい行（再検または同じ種別）、食事はメモへ「別の記入」を追記。元の入力は新しい保存が確保できた後で外す
- 行が取り消されていた（`missing`）ときは〔新しい行として保存〕〔取り下げる〕を出す。定時以外の新しい行は、保存が確保できた後で元の送信待ちを外す
- 読み直しの突き合わせは、画面の欄に加えて送信待ちにある全ての欄（食事のメモなど）で行う
- 血圧の片方を直したら、相方も「値＝基準」の編集として一緒に送る

## 5. 移行とロールバック
- 順序: DB 先（関数の追加だけで、旧アプリは壊れない）→ アプリの配信。新しいアプリ×関数の無い DB は、入力を止めて理由を出す
- ロールバック: 旧ビルドへ戻す。ただし、旧ビルドへ戻している間は、バイタル・食事の送信待ち（`cl_sendQueue2`）は送られない（下の既知の制限 b）。
  新しいビルドへ戻すと送られる。水分・申し送りなどの退避 op（`cl_sendQueue`）は旧ビルドでもそのまま送られる

## 6. 既知の制限
- (a) 応答だけが失われた後に同じ欄を打ち直すと、自分の値どうしで競合として止まる（黙っては消えない。〔くらべて選ぶ〕で選ぶ）
- (b) 旧ビルドへ戻している間、バイタル・食事の送信待ちは送られない。新しいビルドへ戻せば送られる
- (c) 同じ端末の別のタブで同じ欄を打つと、後の入力が勝つ（別の端末どうしの判定はサーバーが行う）
- (d) iOS の Safari では、画面を離れる時の確認（beforeunload）が出ない（アプリ内の画面移動の確認は出る）

## 8. 他の端末が入力中の欄の表示（Presence・表示だけの補助）
保存は妨げない（ロックしない）。記録の保全は §2〜§4 が担う。純関数は `src/lib/presence.ts`、画面の共通フックは `src/hooks/useCellPresence.ts`、
表示部品は `src/components/presence.tsx`、通信は db.ts の `joinPresence`（申し送りの居場所と同じチャンネル `cl_note_presence`。`joinNotePresence` はその上に載る）。

- 配る中身: `{ staffId: number|null, day, residentId, cell?: { table: 'vitals'|'meals', field, slot?, kind?, id? }, at }`
  - 旧版の形（`{ staffId, day, residentId }`）に `cell`・`at` を足しただけ。`slot` は食事の区分（必須）、`kind` はバイタルの種別（省略は定時）、
    `id` は定時以外のバイタルの既存行（まだ行が無い枠は省略）。入力中の値・氏名は配らない（受け取った側が職員名簿で名前を引く。引けなければ「他の職員」）
- 参加（受け取り）は全端末。自分から配るのは、欄に入っている時と、申し送りを書いている時（日報の書きかけ・申し送りフォームで対象を選んだか本文を打ち始めた）だけ。
  見ているだけの端末は配らない。職員を選んでいない端末は staffId=null で配る（相手の画面には「別の端末」）
- 配るのは欄に入った時と、離れて 1.5 秒後の取り消しだけ（打鍵ごとには配らない）。取り消すのは入った時に配った欄そのもの（途中で行 id が付いても外し損ねない）。
  食事一括の量・状態のボタンは、押す操作が確定した時（click）とフォーカスした時に配り、最後の操作から 20 秒か blur の早い方で取り消す（タッチ端末では blur が起きないことがあるため）
- 配っている間は 60〜75 秒ごとに `at` を付け直す。受け取った要素は正規化し、`at` が 3 分より古いもの・自分の鍵（この端末のこのタブ）を捨てる。
  sync が来なくても 15 秒ごとに見直す。申し送りの「いま書いています」表示は `cell` の無い要素だけを使い、申し送りフォームは開いている日の要素だけを出す
- 名前の並び: 同じ職員は1つにまとめ、職員を選んでいない端末は台数でまとめる（「別の端末（2台）」）
- 表示（5画面: バイタル一覧・バイタル一括・食事一覧・食事一括・日報のバイタル欄）:
  - 欄: 破線の枠（--c-info）と、欄の中の角の「✎」印（欄の外へ出さない）。入力要素の aria-describedby で「職員Bが入力中です」
  - 行見出し: 氏名の後ろに「✎」（aria-label「入力中: 職員B」）
  - 表の上の一行の要約: 「✎ 入力中: 職員B（利用者01 体温）・別の端末（利用者03 昼 主食）」。最大3件、残りは「ほか n 件」。
    1行に収めて省略記号、読み上げは全文。表示が無い時も1行の高さを取る（出た時に表を押し下げない）
  - 行の高さ・列の幅を変えない。印刷には出さない
- 接続できない・Realtime が使えない時は何も出さない（例外を出さない）

### 8.1 既知の制限（直さない）
- (e) 旧版の画面（まだ再読み込みしていない端末）は、欄を入力中の要素を申し送りの居場所と読み、「…の申し送りを書いています」と出す。
  職員を選んでいない端末（staffId=null）の要素は旧版には出ない。再読み込みで新版になれば解消する
- (f) 画面を移った直後、前の画面のチャンネルの解放を 5 秒待っても終わらない時（通信が遅い）は参加をあきらめる。
  その画面を開き直すまで、他の端末の入力中の表示が出ない（入力・保存には影響しない）

## 9. 申し送り（notes）の変更・取り消し（2026-09-29 本人承認・段B）

既にある申し送りの変更（本文・対象・記入者・色・重要度・職種タグ・16時以降・時刻・勤務帯・継続の終了）と取り消しも、
バイタル・食事と同じ送信待ち（`cl_sendQueue2` の rows）を通してサーバーで欄ごとに裁く。新規登録は従来どおり insert・client_key。

### 9.1 サーバーの関数 `apply_note_edits`（`supabase/migrations/0017_apply_note_edits.sql`）

```
apply_note_edits(p_id bigint, p_edits jsonb, p_editor bigint default null) returns jsonb
-- p_id=null は関数があるかの確かめ（{version:1,status:'probe'}）
-- p_edits: {欄: {value, base}}。欄は body, resident_id, importance, color, after16, occurred_at, reporter_id,
--          role_tags, shift, ongoing, ended_at, ended_by, deleted_at
-- 返り値は apply_cell_edits と同じ形（row は呼んだ後に生きている行。取り消された・無い時は null）
```

- 欄ごとの判定は 0011 と同じ（いまの値＝あなたの値 → settled／＝基準 → 書く／それ以外 → 競合 changed。基準の無い欄は空の時だけ書く）
- **取り消し（deleted_at）の基準は「呼び手が見た本文」**。いまの本文がそれと一致する時だけ取り消す（見ていない本文を消さない）。
  一致しない・基準が無い → 競合（server には、いまの本文を入れる）。既に取り消されていた → settled
- 行が無い → 全欄 missing。取り消し済みの行 → 同じ値の欄は settled、それ以外は missing（書き換えない・復活させない）
- 本文を空にする編集は拒否（23514）。行を作らない。security invoker・動的 SQL なし・drop → create・authenticated のみ
- 変更の記録を元の利用者から辿るための索引 `idx_record_history_old_resident`（old_row の resident_id）も同じファイルで足す

### 9.2 端末
- 行キー `notes#<id>`（登録後の変更は `notes#ck:<client_key>`・別タブの見ていない入力は末尾 `!<印>`）。エントリに `meta`（日・区分・対象・16時以降＝「送れていない申し送り」の一覧と〔新しい行として…〕の行き先）
- `saveNoteEdits({id}, edits, {meta})`／`deleteNote({id}, 見た本文)`（db.ts）。rev 照合の `updateNote`・`updateNoteFields`・
  `softDeleteNote`・`endOngoingNote` は廃止（関数が無い DB では「サーバー側の更新待ち」で止め、旧経路へ落とさない）
- 旧ビルドが `cl_sendQueue` に積んだ申し送りの update（blocked を含む）は、起動時に `notes#<id>` へ読み替えて移す
  （`cl_sendQueue2` に書けたと読み直して確かめてから外す）。基準が分からないので、退避した時の rev を `baseRev` に持ち、
  送る直前に1行読んで rev が同じなら基準を埋める（違えば基準不明のまま送る＝本文は競合で止まる）
- 基準は「編集を始めた時にサーバーから来ていた生の値」。日報は SheetCell が渡す編集開始時の本文、タイムラインは
  〔本文を直す〕を押した時の本文を控える（自動の取り直しで基準を変えない）
- 画面はサーバーの行に送信待ちの値を重ねて出し、行の下に「送信待ち」「止まっています＋〔くらべて選ぶ〕」を出す。
  送れた（送信待ちから消えた）行はサーバーから読み直す
- 〔くらべて選ぶ〕（ConflictResolver.tsx の NoteConflictResolver）: 〔自分の本文で直す〕〔新しい行として両方残す〕
  （同じ日・区分・対象・自分を記入者・冪等キー固定・登録できてから元を外す）〔先の本文を残す〕（「あなたの本文は保存されません」を
  確かめてから）。相手が取り消していた時は〔新しい行として保存〕〔取り下げる〕
- 「送れていない申し送り」（components/UnsentNotes.tsx）: 日報の各日の上部と設定画面。送信待ち・止まった変更と、登録を待つ・
  拒否で止まった新規登録（cl_sendQueue の insert）を本文つきで一覧し、〔くらべて選ぶ／新しい行として登録／取り下げ〕。
  止まっている件は画面を離れる時の確認（leaveGuard）に数える
- 変更の記録（components/NoteHistoryDialog.tsx）: 日報の行の詳細・タイムラインのカードから、1件ずつ（table_name='notes' と行 id）
- 書きかけ（cl_dailyDraft・cl_draftNote）はタブごとに分けて持つ（src/lib/noteDrafts.ts）。24時間では消さない

- 0017 が無い DB（関数の有無の確かめで missing）でも、保存済みの申し送りの変更は捨てずに送信待ちへ積む。送る時に関数が無ければ
  消さずに間隔を空けて送り直し（その間もバイタル・食事は送る）、関数が入ったと確かめた時にすぐ送る。行には「サーバー側の更新待ち」と出す
- **登録（insert）の op の中身は一度作ったら二度と書き換えない**（2026-09-29 第3巡・チーフ裁定。継ぎ当てをやめて不変条件にした）。
  新規登録は画面が冪等キーを決めて送り（insertNote の clientKey）、登録を押した後にその行へ加えた変更（応答待ちの間・送信待ちの間・
  再読み込み後）は、すべて送信待ち（cl_sendQueue2）の行キー `notes#ck:<client_key>` に {value, base, ver} で積む（基準＝登録で送った値。
  2回目以降は値を後の方に、基準は先の方を保つ）。積む時は保存を読み直しで確かめてから書きかけ・画面の控えを外す（外す→積むの順を作らない。
  確かめられなければ書きかけを残す）
- 送信側: `notes#ck:X` は、登録の op が送信待ち（cl_sendQueue・同じ端末の他のタブの分も）に残っている間は待つ。無くなったら client_key で
  行を探し（findByKeyResult。読めない・まだ無い時は間隔を空けて待つ＝消さない）、見つかれば `notes#<id>` へ付け替えて apply_note_edits で送る
  （付け替え先に既に変更があれば基準は先の方・値は後の方。基準が今の行と違えば競合として端末に残り〔くらべて選ぶ〕に出る）。
  同じ送信の中で、登録を送った後にもう一度送る
- 登録の再送が冪等キーで「既に届いている」（23505）になった時は外すだけ（op は書き換えていないので、後の変更は `notes#ck:X` にある）
- 登録が恒久的に拒否された（cl_sendQueue の insert が rejected で止まった）時は `notes#ck:X` を消さず、「送れていない申し送り」に
  「登録できなかった申し送り」として登録の中身に変更を重ねた本文で出し、〔新しい行として登録〕（冪等キー nr-<元のキー>・登録できてから
  元の op と、合わせた版の `notes#ck:X` を外す）〔取り下げ〕を選べる。新しい行にする時、分けて持つ入力 `notes#ck:X!<印>` は
  新しい行への変更 `notes#ck:nr-X!<印>` へ移す（基準は見ていた値のまま＝新しい行の本文と食い違えば〔くらべて選ぶ〕に出る）。
  〔取り下げ〕は一覧で見せた版の欄だけを外す（見せた後に積まれた変更・分けて持つ入力は外さない。第4巡 R4-2）
- 送り先の登録が無い `notes#ck:X`（登録が送信待ちにもサーバーにも無い＝取り下げた・新しい行にした後に積まれた変更）は、送らずに
  「止まっている」件（state=rejected）にして照会を止め、一覧に「送り先の登録が無いため送れません」と出す（〔新しい行として登録〕
  〔取り下げ〕で回収。画面を離れる時の確認に数える。その行へ新しい入力が積まれた時だけ、もう一度確かめる。第4巡 R4-2）
- 登録の応答の後に応答待ちの間の変更を積む間（await）に同じ行へ確定した入力も、読み直して差分が無くなるまで同じ宛先
  （`notes#ck:X` または `notes#<id>`）へ積んでから、行を送信待ちの登録の行にする・書きかけを外す（第4巡 R4-1）。
  送信待ちの登録の行を直す時の基準は、前後の空白を除いた値（登録で送った値と同じ形。R4-3）
- 本文の確定・対象/記入者の選択は、書きかけと行を控え（ref）から読み、書きかけを直す・外す時は控えも同時に直す。
  登録の応答の直後・描画の前に同じ行で確定しても、二度目の登録にせず、登録できた行への変更にする（savedFromDraft）
- 行・書きかけが画面に無い時（日付を送った・行が置き換わった）に届いた本文も捨てない（第5巡・keepNoteBody）: 登録できた行 →
  notes#<id>／送信待ちの登録 → notes#ck:<ck>／保存済みの行 → notes#<id>／分からない・積めなかった → その日の書きかけの控え
  （別の控えのタブ `<タブ>-kept` へ直接書く＝画面が閉じる途中でも残り、次に開いた時に和集合で戻る）
- 送信待ちの登録の行には、画面の一言が無くても（再読み込みの後も）送信待ちの印を出す。登録が拒否・競合で止まっていれば
  「登録できなかった申し送り…一覧で選んでください」を出す（syncRegistrationRows が登録の状態を行へ写す）
- 行の下の送信待ちの印・「送れていない申し送り」の最大幅は、日報の枠（表の横スクロールの領域）の実測の内幅（--dsheet-view-w）に収める
- 画面: 送信待ちの登録（この日の分。他のタブ・前の起動の分も）を行として出し、`notes#ck:X` の値を重ねて「送信待ち」で出す（再読み込み後も同じ）。
  その行を直すと `notes#ck:X` に積む。登録が送れたら行を外して日を読み直す
- 別のタブ（前の起動を含む）が積んだ送信待ちの値を見ないまま打った入力は、同じ欄に重ねず `notes#…!<印>` に分けて持つ（送ると競合になり
  〔くらべて選ぶ〕に出る＝後の入力が先の入力を黙って消さない）。画面は送信待ちの値を重ねて出し、その値を「見ていた値」として渡すので、
  自分の続きの入力は分けずに重ねる（自分どうしで競合しない）
- 旧ビルドへ戻して畳まれた `notes#ck:X`・`notes#…!<印>` も brokenRaw から救い出す（rescueBrokenLine）
- 前の版（第2巡）が cl_dailyDraft に書いた「確かめ待ち」の印（verifyKey 等）は読まず、普通の書きかけとして戻す（旧 v:1 の読み手も同じ）
- 本文欄（SheetCell）は、確定しないまま外れる打ちかけ（行の置き換わり・編集できなくなる）を onAbandon で渡す。日報はそれを
  登録できた行 → `notes#<id>`／送信待ちの登録の行 → `notes#ck:X`／まだ送っていない書きかけ → 書きかけ、へ振り分ける
- 書きかけを別のタブから引き継ぐ時は新しい行の印を振り、元の行を from でたどる（印を共有しない）。登録・破棄の印は「その時刻までの版」だけを
  外す（元のタブが後から直した版は外さない。重複は許すが消さない）

### 9.3 既知の制限
- (g) 旧ビルドへ戻している間、申し送りの変更の送信待ち（cl_sendQueue2 の notes#<id>・notes#ck:）は送られない。旧ビルドは読めない行を
  cl_sendQueue2 の brokenRaw へ畳んで rows から外して書き戻すが、新しいビルドへ戻すと読み込み時に brokenRaw から救い出して送信待ちへ
  戻す（書き戻しを読み直して確かめてから brokenRaw から外す）。同じ申し送りに新しい入力があって中身が食い違う時は、救い出した方も
  brokenRaw に残し、「送れていない申し送り」に別の本文として出す（〔新しい行として登録〕〔取り下げ〕）
- (h) 画面を離れる時の確認は、止まっているのが送れていない申し送りだけなら「この端末に残ります」と出す（leaveGuard の LEAVE_BODY_NOTES。
  バイタル・食事など画面の中にしか無い入力がある時は従来の文言）
