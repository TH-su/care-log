## ① 性能監査

**結論: 構造は合格。ただし「3系列」は数え違いで、既読集計が設計から漏れており、素朴に実装するとタイムライン1チャンクのペイロードが想定の2倍になる。**

- **行数見積りの妥当性**: 33名・申送34件/日等の基数は計画書 L36-39 の実測と一致。10年で合計約240万行・約340MB は妥当（水分150行/日・既読10人/件は仮定と明記済みで誠実）。無料枠500MBに対し10年で7割は成立するが、**最大表 note_reads(約125MB) は仮定依存**であり、実測1ヶ月後に再見積りすべき。
- **日チャンク＋keyset は正しい**。offset 不使用・日付境界がカーソルを兼ねる構造は全件ロードを構造的に排除する。ビューア側の縮約実績（読取セル 359,464→39,734・88.9%減）の引用も実在を確認（テーマ `gas/DEPLOY-申送ビューアGAS.md` L115）。
- **数え違い**: 設計2は初期フェッチを「3系列並列」とするが、タイムライン1日を構成するのは **notes / vitals / meals / fluid_intake / outings / note_reads / import_days の7種**。特に note_reads は「✓既読5」「未読3」チップの描画に必須で、10日分＝約340注記×10人＝**約3,400行/チャンク**が素朴なJOINレス取得で毎回流れる。**RPC `timeline_chunk(from_date, to_date, staff_id)` 1発で notes に read_count・my_read を畳み込んで返す**形へ確定すべき（往復1回・ペイロード半減）。
- **索引の抜け**: notes に `(resident_id, note_on desc) where deleted_at is null` が無い。個人カルテの「関連申し送り」と記入者絞込がこの索引無しでは note_on 全域スキャンになる。
- **部分索引の使用条件**: `where deleted_at is null` 付き索引は、クエリ側が `.is('deleted_at', null)` を明示しないと使われない。db.ts の全読取に機械的に付与する規約を明記のこと。
- **検索**: pg_trgm 基線＋2文字クエリの弱点認識＋pgroonga昇格の実測ゲートは正しい判断（12.4万行・60MBなら seq scan でも実用域の見込みに同意。ただし「全期間」プリセット×2文字が最悪ケースなので、全期間は3文字以上に制限するか実測で裁定）。
- **描画系（設計2）**: 仮想スクロールライブラリ不採用＋content-visibility＋60日DOM上限は、可変高カード・sticky見出しとの相性を踏まえた正しい選択。フォールバック（DOM上限のみで成立）があるため content-visibility 未検証（Safari 18未満）でも破綻しない。数値目標（初期<1,000ms・60fps・追加<500ms）は検証可能な形で書かれている。

## ③ データ保護監査

**結論: soft delete＋rev トリガ＋delete ポリシー不存在の三段構えは優秀。しかし「バックアップ」が設計のどこにも無い。これは dev-principles 原則4 の明示要求（バックアップ）に対する欠落であり承認ブロッカー。**

- **バックアップ欠落（high）**: Supabase 無料枠には自動バックアップが無い（日次バックアップは Pro 以上・確信度高）。介護記録の正本を置く以上、**夜間 `pg_dump`（Mac launchd・直結接続文字列・ローカル保存＋世代管理）と復元試験（別プロジェクト/ローカルPostgresへ・M-026により本番復元試験はしない）**を設計に必須追加。
- **M-039 対応は本家より進歩**: rev 加算をクライアント規律でなく DB トリガに置き、「書く側の義務」を構造化した点は M-039 の教訓（版数照合は書く側の義務）を正しく反映。ただし M-039 のもう半分「**拒んだ後の復帰経路＋入力は消えていない旨のエラー文**」を db.ts の競合ハンドラ仕様として明文化すること（Realtime 受信で rev を最新化する経路があるのは良い）。継続終了（ended_at）と本文編集が **notes の同一行を書く2画面**である点は M-039 の再現条件そのものなので、両経路とも rev 照合＋新rev受領を実装時に機械列挙で確認する。
- **M-024/026/029**: importer の両方向計数・import_key 冪等・実物構造（EVENTS_HEADERS 等・実在確認済み）からの機械確定は模範的。ただし「**期間をコミットしない**」は PostgREST 経由では実現不可（クライアント側トランザクションが無い）。**直結Postgres接続（pg ライブラリ）でのトランザクション、または期間一括投入RPC**を明記すること。
- **M-038 同型リスク**: オフラインキュー保持中に Supabase Auth セッションが失効すると、再送が401連発で詰まる片道構造になり得る。**401検知→キュー保全のまま再ログイン画面→成功後に自動再送**の復帰経路を設計に明記。
- **M-027（サーバー層の防御）**: rev トリガ・check 制約・delete ポリシー不存在はいずれも端末のコード版に依存しない層にあり合格。大量 soft delete の検知ガードは無いが、soft delete は可逆（deleted_at を null に戻せる）ため low。
- 既読180日削減: delete ポリシーが無い設計と矛盾するため、実行主体（pg_cron または service_role ジョブ）と承認手順を明記（low）。

## ⑦ 移行監査

**結論: import_days による「記録なし/未取込」区別・冪等・両方向計数は模範的。並走期間の書込主体だけが未定義で、ここが最大の事故予備軍。**

- **二重記録衝突（high）**: 並走中に care-log 入力を解禁すると、スプシ手入力→importer 行と care-log ネイティブ行が部分unique（resident_id, measured_on）で衝突し、どちらが勝つか未定義。修正案: **切替日Dまで care-log の入力UIを機能フラグで封鎖（閲覧・検証専用）**＋importer は import_key 無し行が既存の (resident, day, slot) を **skip として計数**（上書きしない・M-024の計数式に含める）。
- ingestedDates 直近200日保持（INGESTED_MAX=200・L1542 実測確認）→ 200日超の遡及は events 行の存在自体から取込済み日を再構成できるが、「その日に1件も記録が無い日」は区別不能になる。残課題として挙がっており妥当。
- 再検・経過観察の過去分: 蓄積スプシ vitals は「日×入居者で1行・5値」（L138-142 実測）のため **kind='recheck' の移行元が存在しない可能性が高い**。移行対象外と明記し本人合意を取ること（未検証・low）。
- 切替の観測条件が未定義 → 検証計画に定義した（verificationPlan 参照）。

## ⑧ 2設計間の矛盾

1. **チャンクサイズ**: 設計1「5日チャンク」vs 設計2「初期10日＋追加10日」→ **初期10日・追加10日・RPC1発**に統一（要求原文「直近10日分」に整合）。
2. **下書き保存**: 設計1保持 vs 設計2非保持 → ④の裁定案で承認時確定。
3. **localStorage プレフィクス**: clg_ vs cl_ → cl_ に統一。
4. **行単位UPSERT（設計2 §6）×部分unique索引（設計1 §1）の非互換（high）**: PostgREST の on_conflict は部分unique索引の WHERE 述語を指定できず、`upsert(onConflict:'resident_id,measured_on')` は「一致する一意制約なし」エラーになる見込み（確信度: 高。ただし M-029 に従い**実装前スパイクで実証**する）。修正案: db.ts は upsert を使わず「**グリッド表示時に既存行idを把握→無ければ insert（409＝他端末が先行→再読込して update へ切替）／有れば update(id, rev)**」方式に統一。部分unique は防波堤として残す。
5. 既読表示（設計2）×既読主体（設計1）の欠落 → ⑥のとおり。
6. タイムライン構成データの数え違い（3系列 vs 実質7種）→ ①のとおり RPC 集約で解消。
