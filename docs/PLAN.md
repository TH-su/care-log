# 申し送り・バイタル記録アプリ「care-log」新規開発 計画書（L0承認依頼版）

## Context（なぜ作るか）

介護現場の「申し送り・バイタル・食事摂取・水分量」記録は現在 Google スプレッドシートで運用しており、動作遅延を避けるため **10日ごとにファイルを作り直す** 非効率な運用になっている。これを撤廃し、何年分蓄積しても重くならない専用アプリ（DB保存＋範囲フェッチ＋高速検索＋個人別カルテビュー＋スプシ風10日タイムライン）へ移行する。設計はサブエージェント3体（DB／UI／QA監査）＋差し戻し1巡で確定済み。**実装は本計画の承認後にのみ着手する。**

## 調査で確定した事実（2026-08-27 実測）

- **入力アプリは存在しない**（重複開発ではない）。既存 `moushiokuri-viewer.html`＋取込GASは完全読み取り専用のビューアで、入力は現行スプシ手入力。ビューアのデータ項目定義（バイタル5値・食事0〜10×6値・イベント列）を新DBが踏襲する
- **バックエンドの現実解は Supabase のみ**（PHP/Node/SQLite が動くサーバーは存在しない。GASスプシは書込量・排他で不利）。kitchen-app（Vite+React+TS+Tailwind+Supabase+GitHub Pages）が社内唯一の SPA+RDB 前例で、Auth/RLS/冪等migration/読み取り専用GAS連携（wsClient.ts）の実装資産をそのまま流用できる
- 現行スプシ実測: 33名（1階11・2階21-22・居室昇順）／申し送り約34件/日（日勤23・デイ3・夜勤8、夜勤に記入者欄なし）／バイタル定時1回+再検0-3件/日（空欄=未測定）／食事0〜10×朝昼夕×主副（「外出」=欠食）／**水分量の列なし**（本文に cc/㎖ 混在で埋没）／「※前シートからの再掲」手作業17回/期／しきい値凡例: 体温≤35.5青・37.5-38.0黄・≥38.1赤、BP上≥151赤・<90黄、BP下≥91赤・<50黄、脈<40黄・≥101赤、SpO2<93黄・<90赤
- 既読・重要度・職種タグは現行に構造なし → 新設（要望どおり）
- 移行元は蓄積スプシ（取込GASが30分毎に集約済み・`apiEvents`/`apiMeasures` で期間取得可・実在パス `~/Claude/Repos/gas-sync/moushiokuri-viewer/コード.js` で列構造を実測確認済み）

## 設計1: DB・検索・バックエンド（Subagent 1・監査反映済み）

**テーブル11**（業務8＋設定1＋運用2・冪等DDL・delete ポリシー不作成=物理削除構造的不可・soft delete のみ・updated_at トリガで rev 自動加算=M-039対応）:

- `residents`（利用者スナップショット。正本=master.gs getRoster 最小射影。source_id+氏名の二重照合 M-034・不一致は needs_review 保留）
- `staff`（職員スナップショット。正本=統合GAS staff。氏名変更=新行+旧行inactive。将来の個別アカウント用 auth_uid 列を予約）
- `vitals`（1行=1測定。kind: routine/recheck/observation で定時・再検・経過観察を統一。温度等は check 制約で範囲検証・数値化不能原文は raw_flags 保持）
- `meals`（1行=1食。main/side 0-10・status: eaten/out/hospital/refused・snack 枠あり）
- `fluid_intake`（1行=1飲水・amount_ml。**水分量を初めて構造化**。日合計はクエリ算出）
- `notes`（申し送り。shift: day/daycare/night・facility・category・resident_id null=全体連絡・role_tags[]・importance 3値・ongoing+ended_at=「再掲」置換の継続フラグ・reporter_id は移行夜勤分 null 許容）
- `note_reads`（既読: note_id×staff_id）／`outings`（外出・外泊・帰着未定=end null）
- `app_settings`（0009流用＋`native_input_enabled` 切替フラグ）／`import_days`（日別取込台帳=「記録なし」と「未取込」の区別）／`master_sync_log`（マスタ同期の増減両方向計数 M-024）

**取得系**: RPC `timeline_chunk(from,to,staff_id)` 1発で7種データ（申し送り+既読畳み込み・バイタル・食事水分・外出・継続ピン・取込状態）を返す。初期10日+追加10日、日付境界 keyset・offset不使用。10日チャンク≈3,260行≈300KB（gzip後≈50KB）。目標: サーバー<20ms・E2E 初期 p95 500ms。個人カルテは (resident_id,日付desc) 部分索引+期間指定必須。**全読取は db.ts に集約**し `.is('deleted_at',null)`+limit を機械付与（部分索引の使用条件・全件ロードの構造的排除）。

**検索**: 利用者名=33名メモリ内0ms。本文=pg_trgm GIN+ilike（debounce 250ms・IME composition 対応・最小2文字・既定90日）。2文字クエリの索引不使用は既知の弱点→実測で seq scan 実用域を確認、超過時のみ pgroonga 昇格、両方不可なら2段検索へ縮退（要実測と明記）。

**書込・同期**: upsert 全廃（PostgREST×部分unique非互換の見込み・スパイクで実証）→ id把握→insert（23505=他端末先行→再読込しupdate）／update(id,rev)。rev 0行=競合→再読込UI・入力は消さない。Realtime購読で表示ウィンドウ内をパッチ。オフライン=送信失敗キュー `cl_sendQueue`（保全ゲート後にのみ消去）・401は**キュー保全のまま再ログイン→自動再送**（M-038対応）。

**マスタ連携**: クライアント pull 型・起動時+TTL60分・読み取り専用・書込アクションのコードパス不作成（wsClient.ts 同型）。GAS読取増 +72〜150回/日（クォータ1%未満・概算）。

**移行**: importer は Mac ローカル Node+pg 直結（session pooler・接続文字列は環境変数のみ）で期間トランザクション。import_key で冪等。計数式 **源泉=inserted+updated+skipped+native_skip+unmatched** 不成立なら rollback（M-024）。facility/kind 列も受け皿あり・列単位落丁も計数。再検履歴は移行元に無い可能性が高く**移行対象外**（切替日以降に蓄積・要合意）。

**バックアップ（監査 high→新設）**: launchd 夜間 pg_dump（03:30・custom形式）→ `~/Claude/Backups/care-log/` 日次14世代+月次12世代・48時間超で鮮度アラート（無料枠の自動一時停止も検知）。復元試験はローカルPostgresのみ（M-026）・手順をREADMEに記載。

## 設計2: フロントエンド・HIG・スプシ風タイムライン（Subagent 2・監査反映済み）

**構成**: `data-ds="ops"`＋スティッキーヘッダ（保存状態・**操作者チップ**・検索）＋5タブ（タイムライン/記録/カルテ/検索/設定。<768px=ボトムタブ・≥1024px=左レール）。主要導線すべて2タップ以内。

**操作者（actor）モデル（監査 high→新設）**: 認証=施設共有アカウント（Supabase Auth）と「誰として記録・既読するか」を分離。起動時＋日替わり/4時間無操作＋明示切替で職員ピッカー。`cl_staffId` に**数値のみ**保持・staff スナップショットとホワイトリスト照合・不正値は再選択へ。**既読付与は明示操作のみ**（本文展開 or 既読ボタン。表示系から書かない=同期原則9）。

**タイムライン（スプシ風10日）**: 日付逆順・1日=1セクション。sticky 日付ヘッダ（✓取込済/「未取込」網掛けバッジ＋サマリチップ: 申し送りn件(未読n)・▲発熱n名・▲低摂取n名・外出n名。チップは見た目32px+疑似要素で44pxヒット）→ ピン留め（‼最重要・継続）→ 申し送りカード（時刻|対象|職種タグ|重要度記号、本文2行clamp=覗き見配慮、記入者・✓既読n・未読は左罫アクセント）→ 外出・外泊（帰着ボタン付き）→ バイタル（既定=異常者のみ・「全33名の表」で日内アコーディオン=スプシ同型全員表・空欄は「—」で未取込と区別）→ 食事（既定=低摂取・欠食者のみ・展開で全員表+水分ml）。記号体系: ↑↑赤/↑黄/↓黄/↓↓青・✓・▲・‼・—・「未取込」（色だけに頼らない）。

**無限スクロール**: 10日チャンク+IntersectionObserver（rootMargin 600px）+`content-visibility:auto`。DOM上限60日（超過は古い側アンマウント≈5,000ノード以内）。**仮想スクロールライブラリ不採用**（可変高+sticky と相性が悪くカクつきの主因。fps 不足の実測時のみ再検討）。目標: 初期<1,000ms・60fps・追加<500ms。

**個人カルテ**: 氏名/居室ヘッダ＋期間セグメント（既定2週）＋**自前SVG折れ線4パネル**（体温/血圧2線/脈/SpO2・しきい値帯+数値ラベル・欠測は線を切る=補間しない・44pxヒット点・aria-label+表フォールバック。外部チャートlib不採用=+80KB回避）＋食事水分履歴表＋本人分申し送り（タイムラインと同一部品）。

**入力UX**: バイタル一括グリッド（フロア別・居室昇順・行高56px・画面下固定キーパッド56×64px=手袋対応・前回値ゴースト・「365」→36.5自動小数・範囲外インライン警告・自動送り・**1名分ずつ自動保存**+未送信可視化）／食事=0〜10の11セグメント（44×44）+外出トグル+水分加算チップ(+100/150/200ml)+Undo／外出外泊フォーム（帰着未定対応・帰着は時刻のみの部分更新）／申し送りフォーム（勤務帯自動初期値・対象・職種タグ・重要度3ボタン・**継続フラグ=「再掲」手作業17回/期を置換**・記入者=操作者初期値・登録後8秒Undo）。削除=確認+論理削除・枠線dangerボタン。

**規約適合**: 本文16px（ops規約）+申し送り本文18px・44px/8px・3状態全画面・コントラストはトークン実測ペアのみ・Tailwind theme を**トークンで置換**（直書きクラスが存在できない）+CI で arbitrary value 検出・200%/ダーク/reduced-motion対応・リロード現在地維持（`cl_view` 等ホワイトリスト・業務データ不保存。例外は cl_staffId=数値のみ・cl_sendQueue/cl_draftNote=データ保護レイヤーとして別掲）。

## ★承認時にご確定いただく事項（推奨値つき・そのまま承認なら推奨値で進める）

1. **認証方式**: 共有アカウント＋操作者ピッカー（推奨）。操作者は自己申告のため証跡性は弱い（職員個別アカウントなら強いが運用負荷増。将来移行はスキーマ変更ゼロで可能）
2. **操作者の再確認頻度**: 日替わり or 4時間無操作で「（職員名）として記録します」ワンタップ確認（推奨）
3. **書きかけ申し送りの下書き保持**: 24時間期限・送信成功/明示破棄で即削除（推奨。共有iPadへの平文残留と記録消失防止の折衷）
4. **出勤者14名+施設長ブロック**: アプリのスコープ外とし、ワースケ/シフトアプリ参照で代替（推奨。必要になれば daily_notes 1表を後日追補）
5. **本文フォントの1px差**: 基本16px（opsトークン規約）＋申し送り本文18px で「17px以上」要件を実質充足（推奨）
6. **移行範囲**: 蓄積スプシから遡れる全期間を取込（200日超の遡及可否は実データで確定・未検証）。再検・経過観察の過去分は移行対象外（推奨）
7. **既読データの定期削減（180日超）**: 当面実施しない（推奨。稼働1ヶ月の実測で再判断。無料枠500MBの逼迫は10年後）
8. **切替日D**: 並走14日間で「importer計数一致100%・未取込0・ビューアと日別件数3日連続一致・パイロット1シフト完遂」が揃ってから本人決定（推奨）
